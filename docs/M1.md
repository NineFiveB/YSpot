## Feature scope (SPEC §10 M1), in build order

Phase 1 — minimum dogfoodable (the switch-over set):

1. **App launching** (§7.1): Win32 via Start Menu folders + UWP via
   `AppsFolder`; the launcher's most-used function. **DONE (2026-09-03).**
   `AppsFolder` enumerated on a worker thread into an atomically swapped
   snapshot (137 apps in 483 ms on the dev box), refreshed on a show older
   than 5 minutes and every 30 minutes; matching on the index's own tier
   scale so apps and files interleave under one global score; launching via
   `IApplicationActivationManager` for packaged apps and `ShellExecuteEx` on
   the item for Win32 (with the `runas` secondary action on Ctrl+Enter);
   icons extracted off the query path into a memory + disk cache and served
   as `data:` URIs; per-user frecency in SQLite at
   `%LOCALAPPDATA%\YSpot\frecency.db`, bounded under the tier gap so an
   exact-prefix match always outranks a frecent lower tier (§7.1).
   Measured: keydown→results-applied unchanged at p50 ~8.5 ms, all buckets
   PASS.
2. **File search actions** (§7.3): open, reveal in Explorer, copy path, copy
   file — the index already answers; the UI grows verbs. **DONE
   (2026-09-03).** Six verbs in the unelevated shell: open, Open With
   (`SHOpenWithDialog`), Reveal in Explorer (`SHOpenFolderAndSelectItems`),
   Copy Path (`CF_UNICODETEXT`), Copy File (`CF_HDROP`), and Delete to the
   Recycle Bin (`IFileOperation` with `FOF_ALLOWUNDO`; the permanent-delete
   APIs are forbidden by §7.3). Reached through the §5.7 Ctrl+K action panel
   (type-to-filter, same Up/Down/Enter/Esc rules) and by direct chords. The
   clipboard and Recycle Bin tests are `#[ignore]`d so a developer's
   `cargo test` cannot replace their clipboard; CI runs them with
   `--ignored`.
3. **Tray icon + single instance** (§5.5) and **autostart** (§5.4): the
   launcher must survive logon and be recoverable when hidden. **DONE
   (2026-09-03).** Tray icon with left-click toggle and a context menu (Open,
   Pause/Resume indexing over the pipe, Start with Windows, Quit — Quit exits
   the shell only, never the service). Single instance via the Tauri plugin
   §5.5 names: a second launch forwards a show and exits 0, verified live.
   Autostart writes `HKCU\…\Run` = `"<exe>" --hidden` from the shell, never
   the installer, with `get_autostart`/`set_autostart` commands ready for the
   Settings UI.
4. **Multi-monitor placement** (§5.3). **Already met since M0**: cursor
   monitor via `MonitorFromPoint`, work area, centered, top edge at 20%,
   680 logical px clamped to 90% of the work area, scaled by the monitor's
   effective DPI and recomputed on every show, so hot-plug and DPI changes
   need no persistent state. Unit-tested for 96/144 DPI, narrow work areas,
   and negative-origin secondary monitors.

Phase 2 — daily-driver parity:

5. **Calculator** (§7.7) — inline evaluation, copy on Enter. **DONE
   (2026-09-03).** A deterministic engine in the shell (no JS eval, no
   external process): a tokenizer, a precedence-climbing parser and an `f64`
   evaluator covering arithmetic with parens, percentages the way a
   calculator means them (`200 + 10%` is 220), `0x`/`0b`/`0o` literals and
   bitwise work with the answer echoed in hex, unit conversion across
   length/mass/data/time/speed/temperature, and `days until <date>`. The
   answer is the first row and Enter copies it. Currency is **deferred** —
   it is the one item of §7.7 that needs a network fetch and a rate
   provider, which is a dependency and a third-party choice rather than an
   implementation detail.
6. **ms-settings catalog + Control Panel tasks** (§7.2). **DONE
   (2026-09-03).** 94 entries (74 Settings pages, 20 Control Panel items)
   with synonyms, in a JSON file shipped beside the executable so it can be
   corrected without a code release; a compiled-in copy is the floor when
   that file is missing or unparseable. Gates (`min_build`, `requires`) are
   evaluated once at startup so a page this machine does not have is never
   offered. Settings launch by URI, Control Panel items via
   `control.exe /name`. A guard test asserts the data file's shape, since it
   is meant to be edited without a build.
7. **Settings** (§5.9; the non-wizard half) — hotkey rebind, scope toggles,
   autostart opt-out. **DONE (2026-09-03), as an in-launcher view rather
   than a separate window** — SPEC §5.9 amended, see below. Settings live at
   `%LOCALAPPDATA%\YSpot\settings.json` (machine-local, never roaming), and
   unknown keys survive a round trip so a newer build's file is not gutted by
   an older one. General carries the hotkey rebind with §5.1's flow
   (key capture by `code` so it is layout-independent, F12 and
   modifier-less chords refused, Win chords warned, atomic unregister →
   register → put the old one back on failure, the likely owner named, and
   three one-click alternatives), the autostart toggle, and the theme
   override. §5.1's other half — a chord that was fine when it was saved and
   is held by something else by the time we start — is caught at startup and
   reported on every surface that mentions the hotkey; see the hardening
   review below. The search section is a placeholder: scope toggles need the
   service's `ConfigUpdate` message, which does not exist yet.
8. **Clipboard history** (§7.4) and **window management** (§7.5) — native,
   shell-side; the §7.8 placement table is normative on what must NOT be an
   extension. **Window management DONE (2026-09-03)**: open windows are a
   search source, so switching to one is the same gesture as launching
   anything else. Enumeration uses the documented alt-tab filter (owner-chain
   walk to the last active popup, tool-window and DWM-cloaked exclusions) and
   is cached — it costs a millisecond or two, which is most of the §2.5
   shell-routing budget for something that changes when a window opens, not
   when a key is pressed — refreshed on every summon and on a 5 s TTL.
   Matching covers the title and the process name, so `chrome` finds every
   browser window. The action panel carries all of §7.5's verbs: fifteen
   layout presets, move-to-next-display, always-on-top, minimize, and close by
   `WM_CLOSE` (never `TerminateProcess`). Switching applies §7.5's
   foreground-lock workaround.
   **Clipboard history DONE (2026-09-03)**, and reached the same way:
   a message-only window with `AddClipboardFormatListener` captures text and
   file lists, §7.4's three exclusion formats are honoured before anything is
   read, and the history is an in-launcher view you filter and paste from.
   Storage deviates from §7.4 — see below.

Phase 3 — exit-criteria hardening:

9. **Onboarding wizard** (§5.9): hotkey confirm → service consent (elevated
   MSI, skip path) → scope selection → autostart → diagnostics consent.
   **DONE (2026-09-03)**, as an in-launcher view like everything else. Shown
   once on first run — and once to an existing install, because this is
   where autostart and diagnostics consent are actually given. **Not** shown
   when started with `--hidden`: a window appearing unbidden at logon is
   exactly what that flag promises not to do, so the wizard waits for the
   first summon. Esc leaves without marking it done, because skipping is not
   deciding. Two steps can only report: the service step has no MSI to
   launch until packaging (§9.1) and always offers §5.9's skip path, and
   scope selection needs the service's `ConfigUpdate` message. Both say so
   rather than showing a button that does nothing.
10. **Shell-side OleDB fallback** (§3.1: `107 SCOPE_UNSUPPORTED` routing) and
    **portable mode** (§9.5) — same code path; portable mode is an exit
    criterion. **DONE (2026-09-03).** `ISearchManager` → the `SystemIndex`
    catalog → `ISearchQueryHelper` for the SQL and connection string, then
    the `Search.CollatorDSO` OLE DB provider, with the rowset read through a
    client-owned accessor. One entry point serves both callers, as §9.5
    requires: no service connected (portable or not yet up) and a `107` reply
    for the current generation both route here. Behind the `FileSearch`
    trait §11 Risk 6 asks for. §3.1's "never a silent empty result" is
    honoured — an unavailable index surfaces as "not searchable", and a
    rowset failure is reported rather than returned as zero matches.
    Verified live with no service running: 33–50 real hits per query.
11. **Crash reporting, opt-in** (§8.5). **DONE (2026-09-03)**, minus the
    upload. Structured logging landed first because it was the bigger gap: a
    GUI process has no console, so the shell's log went nowhere on every run
    not launched from a terminal — which would have left the two-week
    dogfood with nothing to look at after a crash. Now
    `%LOCALAPPDATA%\YSpot\logs`, one JSON object per line, five files of ten
    megabytes. Crash capture is WER LocalDumps under HKCU, written **only**
    with consent and removed when consent is withdrawn, so "no consent ⇒
    dumps stay local" holds because no dump is written at all. Dumps are
    rotated. **Upload is not implemented**: there is no endpoint, and picking
    one is a product decision — everything that would feed it is in place.
    §5.9's "log export" ships as "open the folder", which Explorer does
    better than an archiver dependency would.
12. **Accessibility pass** (§5.12): UIA tree, Narrator + NVDA end-to-end —
    exit criterion, not polish; verify per phase rather than at the end.
    **Automatable half DONE (2026-09-03).** The combobox/listbox pattern with
    `aria-activedescendant` was already in place from M0; added since: a
    polite live region announcing the **settled** result set (never per
    batch, which would read "1 result… 8 results… 23 results" for one
    keystroke), an accessible name on the query field, a forced-colors block
    resolving the token layer to system colors with the selected row keeping
    a non-colour marker, and a **contrast test that reads the real token
    values out of `styles.css`** — both themes measure AA or better today
    (light 15.5/4.6/4.7, dark 13.7/6.4/6.6 for fg/muted/accent on bg) and
    cannot drift below it without a test going red.
    **The Narrator/NVDA end-to-end runs are deferred out of M1**
    (2026-09-04, at the author's ruling; SPEC §5.12 amended). They needed a
    person listening and nothing automated stands in for them. The markup
    above is therefore believed correct rather than known to be — a reader
    that says nothing as the selection moves would look exactly like this.
13. **CI keeps M0 budgets green.** **DONE (2026-09-03):** the shared-runner
    `bench` now runs with `--strict`, so a p95 or memory budget miss fails
    the build rather than printing a warning nobody reads. Flipped on
    measured margin, not optimism: across four consecutive runs the worst
    class was 2.2–3.6 ms against the 10 ms per-class budget and memory was
    146.6 B/entry every time, so a transient stall would have to nearly
    triple the worst case to flake. This gates the *shape* of the numbers;
    reference-hardware sign-off stays deferred with Machine B (§10
    amendment).

## Rulings and deviations recorded during Phase 1

- **§5.1 amended: the hotkey can be held by YKeys instead of the shell**
  (2026-09-03). `RegisterHotKey` has no owner query — first claim wins,
  everyone else gets a bare `FALSE` — so a machine running several tools that
  each grab a chord has no coherent owner and no honest conflict story.
  [YKeys](https://github.com/NineFiveB/YKeys) can now hold YSpot's chord.

  The constraint that shaped the design is §5.1's 50 ms hotkey→visible budget,
  which is an M0 exit criterion. YKeys' ordinary bindings start a process, and a
  process that does *nothing* costs 8 ms median / 20 ms p95 / 29 ms max on
  Machine A — measured, not estimated, and 40% of the budget at p95 before
  YSpot's show path begins. So the summons is not a spawn: YKeys gained a
  `@signal:<window class>[#<code>]` binding form that posts
  `RegisterWindowMessage("YKeysSignal")` to a message-only window
  (`YSpot.Signal`, `wParam` = verb), which costs microseconds.

  The load-bearing detail is the foreground hand-off. Pressing the chord makes
  *YKeys* the process Windows permits to foreground; YKeys calls
  `AllowSetForegroundWindow(yspot_pid)` before posting. Without it the launcher
  appears and does not hold the keyboard — §5.2's failure mode, and a silent one,
  which is why `focus::force_foreground` logs a refusal.

  **Verified end to end (2026-09-04)**, without synthesising a keypress:
  `ykeys signal YSpot.Signal#99` against a running shell finds the
  message-only window (`FindWindowEx` under `HWND_MESSAGE`, which `FindWindow`
  cannot see), posts the registered message, and the window procedure
  dispatches it — read back out of the shell's own log as "code 99 is not one
  this build knows". That also proves the hop to the main thread, since the
  unknown-code arm runs inside that closure. **Still unproven: the foreground
  hand-off.** Only a real `WM_HOTKEY` makes YKeys the process Windows permits
  to foreground, so that one needs a person pressing the chord; a refused
  `SetForegroundWindow` is logged on the YSpot side and a refused grant on the
  YKeys side, which is the pair to read if the launcher appears without the
  keyboard.

  `hotkey_source` defaults to `shell`, so nothing changes for an install that
  has never heard of YKeys. It is a setting rather than a guess because from
  inside the process "nobody registered the chord" and "something else
  registers it for us" look identical, and one of them is the fault §5.1
  requires be reported. The signal window listens either way — binding a
  second verb (the clipboard view) should not need a setting flipped first.
- **§5.11 merge/selection, interpretation.** The contract says cross-source
  merge inserts by global score *and* must not move or re-index the selected
  row. Those pull apart only once the user has aimed at something. Until the
  selection is moved, the list is a plain global-score merge and the
  selection sits on the best row — nothing the user is aiming at can move,
  because they have not aimed yet. Once the user moves it, the displayed
  order freezes and later arrivals append below (rule 3, stated literally).
  Implemented in `apps/shell/src/lib/merge.ts` with unit tests; CI runs them.
- **§7.3's File Search command and inline cap — DONE (2026-09-06).** The root
  list keeps its top five file hits by score; `File Search` (also `files`,
  `find file`) opens the full list as an in-place view on the same index and
  the same generation counter, with `kind:document|image|audio|video|archive`
  (expanded to extension sets in the shell, since the service ignores `kind`),
  `ext:a,b` and `path:sub` combining with AND, Enter to open, and the root
  list's own chords and Ctrl+K panel for everything else. Three pieces of §7.3 are deliberately not here: `content:` is
  M2's full-text index; the **preview pane** (thumbnails via
  `IShellItemImageFactory`, syntax-highlighted text) is a body of work of its
  own and is deferred with the same reasoning as clipboard images; and
  `kind:folder` needs a directory filter the protocol does not carry, so it is
  refused by name rather than applied to nothing. In portable mode the view
  says the filters did not apply — Windows Search takes the name only.
- **Icon cache key (§7.1).** Keyed by AUMID + physical pixel size with a
  seven-day TTL rather than by source mtime; SPEC §7.1 amended with the
  reason.
- **Onboarding's service and scope steps are informational** until the
  service MSI (§9.1) and the `ConfigUpdate` message exist. They report the
  real state of this machine and offer the skip path; they do not pretend to
  offer choices that cannot be honoured.
- **Crash-dump upload needs an endpoint decision** before it can be built
  (§8.5). Consent, capture, and rotation are done; where a dump would be
  sent, and who operates that, is not an implementation detail.
- **Degraded-mode file search is slower than the §2.5 gate, by design.**
  The self-measurement reports 17–40 ms for portable-mode queries against a
  20 ms budget. That budget is the *service* path's; Windows Search over OLE
  DB is precisely what the custom index exists to beat, and §9.5 calls this
  state "fast indexing off". It is not a regression of the gated number,
  which is measured with the service running.
- **Clipboard storage uses per-value DPAPI, not SQLCipher** (§7.4, amended
  2026-09-03). Every value a row carries — content and preview both — is
  encrypted individually; the preview is not exempt, because a clipboard
  entry is usually shorter than the preview length and a plaintext preview
  column would hand over exactly what the encryption is for. Verified live:
  after capturing probe strings, neither the database nor its write-ahead log
  contains them. Row metadata (timestamp, source app, kind) stays in the
  clear, and the searchable window is the most recent 1,000 entries because
  each preview costs a DPAPI call; retention on disk keeps §7.4's 10,000.
- **Clipboard images are deferred.** Text and file lists are captured;
  `CF_DIB`/`CF_DIBV5` decoding is a body of work of its own and is not what a
  launcher's history is mostly for.
- **Pasting injects Ctrl+V**, and window switching injects one synthetic Alt
  keypress (§7.5's documented
  foreground-lock workaround). Neither is exercised in an automated run: the standing rule
  against injecting input while someone is at the keyboard covers the
  product's own injection too, so switching is verified by reading the code
  and by unit-testing the pure parts (the tile geometry, the id parsing, the
  matcher), while enumeration and matching are verified live.
- **Settings is a view in the launcher, not a window** (§5.9, amended
  2026-09-03 at the author's direction, Raycast philosophy). You search for
  it and get it in place; Esc pops back to the query, which is §5.7's
  navigation stack. The window recomputes its §5.3 placement for the taller
  view, keeping the top edge fixed and clamping to the work area. `yspot.exe
  --settings` opens it directly, and a second launch with that flag forwards
  to the running shell.
- **Hardware capability gates are partly optimistic** (§7.2). Battery is
  probed with `GetSystemPowerStatus`; cellular, Bluetooth, pen and touchpad
  read as present because probing them needs WinRT or SetupAPI enumeration —
  a dependency for a gate that hides a handful of rows. An offered page that
  opens the Settings home is a smaller failure than a page the machine has
  and cannot find, so they default to shown until that probing lands.
- **Tray menu deviates from §5.5's list** by one entry: an extra "Start with
  Windows" tick (Settings… has been there since Phase 2), which stands in
  for the autostart toggle §5.9 puts in Settings and onboarding. Both move
  when those land. Autostart is therefore **not** enabled on first run as
  §5.4 describes — that write is gated on onboarding consent (Phase 3), and
  turning it on silently before asking would be the wrong default to ship.
- **Clipboard actions leave the launcher open**; everything that hands the
  user to another window dismisses first, so the launcher never floats over
  what it just opened. Only a launch counts as frecency use — copying a path
  or revealing a folder is not what the ranking is about (§7.1 counts
  launches).
- **App catalog is not persisted across restarts.** A cold enumeration
  measured 483 ms and runs at startup off-thread, so the catalog is ready
  long before the first hotkey press in practice. Revisit only if a cold-boot
  measurement shows a real gap.

## What is left for M1, and who has to do it

Everything buildable is built. What remains is either yours to run or yours
to decide:

1. **The two-week exclusive dogfood** — the one exit criterion left that
   needs a person. (The Narrator/NVDA runs were the other; deferred
   2026-09-04.) How to run it, unpackaged: [`docs/DOGFOOD.md`](DOGFOOD.md).
   Release builds of the shell and service were started and checked clean
   on 2026-09-04.
2. **Crash-dump upload endpoint** (§8.5): consent, capture and rotation ship;
   where a dump goes and who operates that is not an implementation detail.
3. **Design-doc Step 12, the open-addressed FRN table** (issue #10) — now a
   smaller decision than it was. The re-derivation that made it look required
   has been measured (design doc §G): the 1M compaction peak is 84–97% of the
   cap from L = 26 to L = 36, so the budget closes without it. Two things
   temper that — the corpus is synthetic, and §10's gate is RSS while the
   measurement is allocator bytes, with M0's run suggesting ~5% on top, which
   puts L ≈ 36 at the line. So: **schedule it for the headroom, or leave it
   and let the reference-volume MFT run decide.** No longer urgent either way.
   The measurement also found and fixed a real defect on the way — compaction
   was allocating a second `arena_recs`, which Step 9's own rule forbids.

Standing constraints carried from M0: the `yspot-m0` injected-input commands
(`toggle`/`type`) are never run while anyone is at the keyboard; Machine B
column of `docs/M0.md` stays open as a post-M0 obligation; issue #7's
tripwire is the bench's fuzzy-survivor table (`capped` column).

## Pre-dogfood hardening review

An adversarial review over the M1 shell diff (five lenses — Win32/COM
resource safety, concurrency, frontend, security, spec drift — each candidate
finding then verified by an independent agent trying to refute it) returned
**19 confirmed findings, 8 of them major**. The verification pass mattered:
it rejected three candidates outright and corrected overstatements in several
that survived, so what follows is the reviewed remainder, not the raw output.

A second adversarial pass (2026-09-04) over everything committed since the
first one — 39 agents, 13 confirmed findings clustering into five — added:

| # | Where | What was wrong |
|---|---|---|
| 8 | `index.rs` | **Pre-existing, and the worst thing found this milestone.** `compact()` rebuilt `owner` with block *b* → the first record *at or after* its boundary, while `push_arena_rec` and the forward walk in `slot_at` both use the last record *at or before* it. The two agree only when a record starts exactly on a 64-byte boundary; otherwise the walk starts one record too far and never moves back, and a hit in the straddling record's tail resolves to the **next file**. Measured: 15–21% of post-compaction searches returned another file's FRN. The existing compaction test tolerated `frn` mismatches at tied scores — which is exactly the symptom — and the `owner` invariant test never called `compact()`. Both now do, and a distinct-token corpus asserts every hit names the file that contains it. |
| 9 | `lib.rs` | My `should_rebind` fix made every save fail while the chord was contested — theme, consents, and the YKeys hand-off that is the *remedy* for a contested chord — because each went through the registrar and took its `Err` as the save's. | 11 | `Settings.tsx` | Under YKeys the chord button was disabled but a capture already in progress stayed armed, and the conflict banner's alternatives were live — either would register a shell hotkey the setting says does not exist. Both gated now. |

**Every finding from this review is now closed.** Seven passes: 19 + 13 + 9 + 2 + 21 + 9 + 5
confirmed. Each pass after the first found regressions in the previous pass's
fix commit, which is why fix commits get reviewed too. The four that were carried
