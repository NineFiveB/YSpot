## How the harness measures

`yspot-m0` injects input with `SendInput`, takes a QPC timestamp immediately
before injection, and consumes one real-time ETW session containing both the
shell's markers (provider `M0_MARKER_PROVIDER` in `yspot-proto`) and
`Microsoft-Windows-Dwm-Core` composition events. The session runs with
`ClientContext = 1`, so every event carries raw QPC — injected keydown, pipe
arrival, rAF apply, and composited frame sit on one clock:

```
keydown ─(pipe+match+decode)─► `results` marker   ← §2.5 ≤ 20 ms p95 gate
        ─(next rAF applies)──► `applied` marker
        ─(compositor)────────► DWM composition    ← "pixels" (≈ +≤2 vsync)
```

Read the endpoints honestly: the `results` marker fires in the shell's pipe
thread after the frame is decoded — before the Tauri event relay and the
WebView2 IPC hop — so the gated column is "results decoded in the shell", a
slight underestimate of "available to the frontend"; the `applied` marker
crosses the webview→shell invoke hop before it is stamped, so that column
carries the hop as overhead.

DWM composition events are **off by default**: enabling the Dwm-Core
Composition provider floods the ETW session hard enough that, on an elevated
injector, it defers the shell's WM_HOTKEY delivery and censors the run (see
the injected-input limit under provisional numbers). The gated endpoints —
`hotkey → shown` (< 50 ms proxy) and `keydown → results` (≤ 20 ms) — are plain
markers and need no DWM. The true pixels endpoint is opt-in via `--with-dwm`,
which also prints the id histogram for `--dwm-ids` pinning; it is advisory
until those ids are pinned, and heavy censoring is expected on an elevated
box.

The markers ship in the production binary (an ETW write with no listener is a
few branches), so the measured build is the shipped build.

## Preconditions — the numbers are invalid without these

- **Elevated prompt** for `yspot-m0 type|toggle|etw-dump|startup|freshness`
  (ETW session creation; MFT enumeration).
- **Idle desktop**: nothing animating, no video, no background window
  repainting. The pixels endpoint attributes the first DWM composition after
  `applied` to the launcher; anything else composing steals that attribution.
- **Hands off keyboard and mouse** during `type`/`toggle` — injected and
  physical input interleave.
- **Node.js** to build the frontend (the ETW markers include frontend-side
  ones; a stale `dist/` silently reports nothing). Install:
  `winget install OpenJS.NodeJS.LTS`. Machine B (Win10 1809): use the Node 20
  LTS MSI, verified working there; newer Node lines are unverified on 1809.
- If local builds fail with `os error 4551`, Smart App Control is blocking
  unsigned build tooling; turn SAC off (reversible on builds ≥ 26200.8116).

## Procedure

Build once (elevated not required):

```
cd apps/shell && npm ci && npm run build && cd ../..
cargo build --release -p yspot-indexd -p yspot-m0
cargo build --release -p yspot-shell        # or: cargo tauri build
```

Then, in an **elevated cmd prompt** (the `::` comment lines are cmd syntax —
in PowerShell, skip them or replace with `#`), in this order:

```
:: 1) Smoke test #1 (also safe unelevated). Run FIRST — it round-trips the
::    clipboard and restores text contents only.
target\release\yspot-m0.exe clipboard

:: 2) Initial index + RSS. Leaves the service running for the later steps.
target\release\yspot-m0.exe startup --drive C: --keep

:: 3) USN event → searchable (needs the --mft service from step 2).
target\release\yspot-m0.exe freshness --iterations 20

:: 4) Start the shell (own window appears; leave it alone from here on).
start target\release\yspot-shell.exe

:: 5) Hotkey->visible (via the `shown` marker, the <50 ms proxy) plus the
::    hidden-throttle report. 50 cycles ~ 2 min. DWM is OFF by default: its
::    composition-event firehose defers the shell's WM_HOTKEY delivery on an
::    elevated injector and censors the whole run (the injected chords queue
::    and drain in one burst at exit). The `shown` marker needs no DWM and is
::    within a few ms of the true pixels endpoint. The FIRST cycle's rafgap
::    line covers the pre-run hidden interval; read it separately.
target\release\yspot-m0.exe toggle --cycles 50

:: 6) Per-keystroke section 2.5 decomposition, bucketed by prefix length —
::    the worst-case 2-char gate reads from the 2-char prefix buckets. The
::    <= 20 ms `results` endpoint is a marker; no DWM needed.
target\release\yspot-m0.exe type --iterations 30

:: 7) OPTIONAL, advisory: the true DWM pixels endpoint and the id histogram
::    for --dwm-ids pinning. --with-dwm re-enables the composition firehose,
::    so expect heavy censoring on an elevated box — the few uncensored
::    cycles still show pixels within a frame of `shown`.
target\release\yspot-m0.exe etw-dump --seconds 10
target\release\yspot-m0.exe toggle --cycles 10 --with-dwm
```

**IME check (manual):** with the window summoned, switch to a CJK IME, type a
composition, confirm candidates render in-place and Enter commits (§5.2/§5.7);
then dismiss and confirm focus returns to the previous window with the IME
still functional. Record pass/fail; there is no automated endpoint for this.

Machine B addendum: the CI latency harness is specified to run on Machine B —
once these numbers exist, wire `yspot-m0 type` into a self-hosted runner job
on that machine; the shared GitHub runner cannot serve (no reference hardware,
no reliable idle desktop).

## Provisional numbers (dev box, NOT sign-off)

Dev machine (Win11 26200, elevated) ≠ Machine A/B, and the volume was C:\ at
**828k files, not ≥1M** — recorded to show the pipeline works, catch
regressions, and de-risk the reference-machine runs. Measured across elevated
harness passes this session.

Service-side gates (no injected input; fully clean):

| Criterion | Gate | Measured (828k files, C:\) |
|---|---|---|
| initial index (MFT enumerate → Tailing) | < 15 s @ 1M | **6.32 s** (6.10 s enumerate, 135,796 entries/s) |
| service RSS after warm queries | < 200 MB @ 1M | **119.6 MB** working set / 120.3 MB private |
| USN create → searchable p95 | < 1 s | **3.16 ms** (n=20; min 2.33, max 4.38) |
| `ram_bytes.filename` | (budget input) | 118.2 MB = **143.0 B/entry** on the real volume |

Smoke tests:

- **Clipboard: PASS**, 3/3 (Win11 26200). `AddClipboardFormatListener` +
  `HWND_MESSAGE` is viable for §7.4.
- **Hidden-WebView2 rAF throttling: NO throttle** — the flagged risk does not
  bite. While the launcher is hidden the WebView2 compositor keeps servicing
  `requestAnimationFrame` at full rate (`max_gap_ms` ~8–10 ms = one 120 Hz
  frame; tick count scales linearly with hidden time), and the **first frame
  after show is 0.8–7 ms**. No cold-start penalty on summon.

Latency (injected-input harness — see the reliability limit below; numbers are
from the cycles that landed):

- **hotkey → shown p50 ~3.7–5 ms, p95 ~4.5–14.6 ms** (gate < 50 ms). The
  `shown` marker is a few-ms proxy for hotkey→visible; the DWM-measured
  hotkey→visible on the cycles it captured was **~7–22 ms**, also well under.
- **keydown → results-applied: worst-bucket p95 19.2 ms, PASS** (gate ≤ 20 ms;
  most buckets 11.5–17 ms, p50 ~9 ms). Measured with the NON-INJECTING
  self-measurement (`YSPOT_M0_SELFMEASURE`): 480 samples, 16 query-prefix
  buckets (1–6 chars) over a 23.5k-entry System32 walk corpus. This endpoint
  is STRICTER than §2.5's gate — it is results *applied in the rAF* (data
  available + webview relay + up-to-one-frame rAF wait), plus the interim
  pipe-poll overhead below — and it still passes. The ~9 ms p50 decomposes as
  ~2–3 ms pipe round trip (probe-verified) + invoke/relay hops + rAF
  quantization. Reference machines re-measure this on ≥1M files.
- **Client-side pipe deadlock found and fixed en route** (the client twin of
  issue #9 / dd228ee): the shell's dedicated read thread + command-thread
  writes on a `try_clone`'d synchronous handle deadlocked the FIRST
  SearchQuery — the launcher could not return results at all. The pipe client
  is now a single-owner pump loop (`PeekNamedPipe`-guarded reads, ≤2 ms poll);
  `FILE_FLAG_OVERLAPPED` remains #9's M1 item.

Memory at 1M **synthetic** entries: 139.1 B/entry warm (`bench`) — under the
200 cap. On real filenames the number is higher and volume-dependent: the 828k
C:\ enumeration above measured **143.0 B/entry**, between the synthetic 139 and
the 554k walk's 165 (that walk oversampled long user-file names). Mean name
length drives it (issue #10); budget headroom on real data is ~55 B/entry here,
tighter on name-heavy volumes.

**Injected-input reliability limit (harness, not product).** `toggle`/`type`
drive the launcher with `SendInput`. On this elevated box the injected
Alt+Space lands for ~4–5 cycles, then queues undelivered until the harness
exits (confirmed in the shell log: window hidden the whole run, ~25 toggles
draining in one burst at exit). It survived every fix tried — DWM provider
off, O(1) event streaming, foreground-lock disabled, summon retries — so it is
a rapid-elevated-synthetic-input artifact, not a launcher latency problem: the
cycles that land are all within budget. For the reference-machine runs, either
inject more slowly (seconds between chords), drive from a non-elevated helper,
or take the numbers by hand with the in-app HUD. And never run these while
someone is at the keyboard — the synthetic input types into the focused
window.
